# 报告数据格式

脚本只渲染已经发生的记录，不生成问题、回答或评价。宿主 AI 在面试结束后准备 UTF-8 JSON；先脱敏，再生成批注引用。结构如下，示例完全虚构，只用于说明格式，不是参考答案。

```json
{
  "title": "模拟面试报告",
  "mode": "demo",
  "summary": ["演示中已说明项目目标，个人动作还需更具体。"],
  "settings": ["目标：产品岗位；中文；完成一轮演示。"],
  "sections": [
    {
      "id": "M01",
      "title": "自我介绍",
      "context": ["来源：岗位类别常见问题。"],
      "turns": [
        {"id": "M01-Q1", "role": "interviewer", "text": "请简单介绍一段相关经历。"},
        {"id": "M01-A1", "role": "candidate", "text": "我做过一个课程项目，主要负责整理需求。具体取舍还没有想清楚。"}
      ]
    }
  ],
  "annotations": [
    {"turn": "M01-A1", "kind": "gap", "quote": "具体取舍还没有想清楚", "note": "补一个做过的取舍，以及当时依据的信息。"}
  ],
  "next_steps": ["选一次实际决策，按背景、动作与结果重练。"]
}
```

- `mode` 必填，只能为 `practice`（用户实际回答）或 `demo`（明确授权的自问自答）。演示在标题旁统一标记，不在每页底部重复说明。
- `summary`、`settings`、`next_steps` 为字符串数组；`summary` 和 `next_steps` 不得为空。总结引用对应题号，未观察的能力单独说明。
- `sections` 是实际练习阶段数组，可为空（例如开始前就结束）；此时报告说明尚无回答，不能虚构能力结论。
- 每节 `id` 和每轮 `id` 必须各自唯一。`title` 是阶段名；可选 `context` 是来源或必要背景的字符串数组。
- 每节 `turns` 完整保留实际记录。`role` 只能是 `interviewer`、`candidate`、`coach`。`text` 为原文字符串，空行分段，不支持原始 HTML 或 Markdown 格式。脚本将字面内容转义，不执行代码。
- 候选人获得提示后的回答加 `"assisted": true`；未给提示用 `false` 或省略。跳过、未答等状态用可选 `status` 字段写在对应阶段，不虚构一个候选人回答。
- `annotations` 可为空。`kind` 为 `good`／`gap`／`tip`。`turn` 必须存在，`quote` 必须在对应 `text` 中唯一出现，并且不能跨段或与同一轮的另一批注重叠；否则脚本报错并要求修正数据，不静默丢批注。选择更完整的原句以消除歧义。
- `note` 是具体短评，不增加新事实；提示后回答的短评明确写出「提示后」。每轮少量标注，保持阅读空间，不强制三色齐全。
- 报告第一页展示总结与本轮范围；各阶段页原句高亮、短评和问答对应；最后显示重练清单。报告文字不会因固定画布尺寸被裁切。

普通练习的用户记录不要通过 `demo` 来掩盖事实来源；没有用户回答就写未观察。仅演示时才能编双方台词，且不把示范表现赋给用户本人。

## 文案与视觉约定

面向求职学生，先看结论、再回看原答。正文内容完整，界面用词尽量短；颜色同时配文字标签：亮点、待补、建议。蓝白阅读布局、原有角色底色和批注各有用途，不为增加批注重排正文或删改用户回答。以后局部改字时先备份当前输出，不覆盖已确认的内容与颜色规则。
